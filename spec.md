Curium Item Master Data Quality Agent – MVP Specification

（Item Master 数据质检智能体 · MVP 规格）

1. Purpose & Scope（目标与范围）

This MVP agent is a data quality checker for Curium’s Item Master data.
It takes the Item Master Excel workbook as input, runs a set of business-driven validation rules, and returns:

A structured JSON result (issues + statistics).

A human-readable summary generated by an LLM (finance-friendly explanation).

The goal is to demonstrate how master data issues in Item Master can be detected early, before they impact:

Inventory valuation on the balance sheet

Cost roll-up & variance analysis

Alignment between ERP transactions and GL accounts

This is a demo / POV tool, not a production system.

2. Main User & Use Case（使用场景）

Primary user:

Finance, Data, or IT person at Curium (e.g., Richard / Gabriel / Tim’s teams)

Or: student team presenting the solution to Curium stakeholders

Typical flow:

User exports an Item Master snapshot from ERP into Excel (same structure as the sample file).

User opens the web page (Next.js app) and uploads the Excel file.

The backend parses the file, runs validation rules, and returns a JSON result.

The UI shows:

High-level stats (how many items, sites, issues, by rule/severity)

A table of detailed issues

The user can:

Download the JSON / CSV of issues

Read an LLM-generated executive summary explaining the risks in plain English

Ask questions like “Which sites have the highest risk of double counting?”

3. System Overview（系统概览）

MVP is one Next.js project, but在开发时用 4 个 Cursor 对话/模块来拆分：

A. Validation Engine Module

Pure TypeScript/JS logic to read the Excel workbook and run validation rules.

B. API Route Module

Exposes /api/validate endpoint to the frontend.

C. Frontend UI Module

Next.js page: file upload + results dashboard + issues table.

D. LLM Summary & Q&A Module

Takes ValidationResult JSON as input, calls LLM, outputs:

Executive summary

Key risks by rule/site

Recommended next steps / talking points

Deployment:

One Next.js app on Vercel（前后端同库同项目，最简单）

Sample Excel file stored in public/sample_item_master.xlsx

4. Data Model – Excel Workbook（数据模型：Excel）

输入是一个包含 4 个 sheet 的 .xlsx 文件，结构与 Curium 提供的一致：

4.1 Sheet: ITMENT – Global Item Master

Role: Global definition of each item (one row per item number).

Key columns (MVP used):

Item number

Item description

Stocking unit of measure

Primary key (for MVP):

Item number

4.2 Sheet: ITMREL – Item–Site Relationship

Role: Which site uses which item.

Key columns (MVP may use, optional in first version):

Site identifier

Item number

Item revision

For MVP, we mainly rely on ITMRVA & ITMRVB for site-level data,
so ITMREL is optional in first iteration.

4.3 Sheet: ITMRVA – Item Attributes by Site

Role: Site-specific attributes for each item (flag, UOM, class, etc.).

Key columns (MVP used):

Site identifier

Item number

Item revision (can be ignored for MVP or used if present)

Inventory flag (1 = inventory item, 0 = non-inventory / expensed)

Unit of measure

Item class

(Optional for later) Effective date from, Effective date to, Unit cost default, etc.

Logical key for MVP:

(Site identifier, Item number)

4.4 Sheet: ITMRVB – Item Cost by Site

Role: Costing data per site/item.

Key columns (MVP used):

Site identifier

Item number

Item revision

Record identifier (e.g., A/B; for MVP we can pick the latest/first)

Standard unit cost

Current unit cost

Logical key for MVP:

(Site identifier, Item number)

If multiple records, choose one deterministically (e.g., latest by Change date or smallest Record identifier).

4.5 Logical “ItemSite” View（逻辑视图）

For validation, we conceptually build a combined view:

ItemSite = ITMRVA
    LEFT JOIN ITMRVB ON (Site identifier, Item number)
    LEFT JOIN ITMENT ON (Item number)


Each ItemSite record represents one item at one site, with:

Global properties from ITMENT

Site-level flags/UOM/class from ITMRVA

Site-level cost from ITMRVB

5. Validation Rules（校验规则设计）

下面是 MVP 要实现的规则列表。
每条规则包含：ID、业务含义、使用字段、触发条件、严重等级、示例错误信息。

5.1 Rule: INV_COST_MISSING

Business name: Inventory item without cost
Business rationale:
Richard 提到：库存账户是资产负债表上的大头，如果库存 item 没有成本，Inventory value 会被低估，影响融资与报表可信度。

Fields used:

ITMRVA.Inventory flag

ITMRVB.Standard unit cost

ITMRVB.Current unit cost

Trigger (pseudo):

If Inventory flag == 1
AND (Standard unit cost is null or 0)
AND (Current unit cost is null or 0)

→ Raise an issue.

Severity: high

Example message:

Inventory item has inventory flag = 1 but both standard and current unit costs are 0 at site MHP. Inventory value may be understated.

5.2 Rule: EXP_ITEM_WITH_INVENTORY_COST

Business name: Expensed item carrying inventory cost (double counting risk)

Business rationale:
会议中反复强调：

“We don’t want to put something into inventory that we’ve already expensed, otherwise we are accounting for it twice.”

如果某个 item 标记为非库存（费用化），却还在成本表里有标准成本，很可能意味着它被当成资产处理，存在 double-count 风险。

Fields used:

ITMRVA.Inventory flag

ITMRVB.Standard unit cost

ITMRVB.Current unit cost

Trigger:

If Inventory flag == 0
AND (Standard unit cost > 0 OR Current unit cost > 0)

→ Raise an issue.

Severity: high

Example message:

Non-inventory (expensed) item has non-zero standard cost at site MHP. This may indicate double-counting between expense and inventory.

5.3 Rule: UOM_MISMATCH

Business name: Inconsistent unit of measure between global item and site attributes

Business rationale (Tim 的例子）：

采购认为 “1 unit = 1 box（盒子里有 10 个）”

财务认为 “1 unit = 1 each (EA)”
→ 价值计算会出现 10 倍偏差。

Fields used:

ITMENT.Stocking unit of measure

ITMRVA.Unit of measure

Trigger:

For a given Item number + Site identifier:

If Stocking unit of measure (from ITMENT) is not null
AND Unit of measure (from ITMRVA) is not null
AND the two strings are different (case-insensitive comparison, trimming spaces)

→ Raise an issue.

Severity: medium

Example message:

Stocking UOM in ITMENT is 'BOX', but site-level UOM in ITMRVA is 'EA' for item N10003. Procurement and finance may value quantities differently.

5.4 Rule: ITEM_CLASS_INVALID

Business name: Item class missing or not in the standard list

Business rationale:
Richard 说过：如果 Item class 完全乱掉，“it doesn’t matter what we have on the GL, it’s not gonna be right”。
错误或随意的分类会导致成本 roll-up 到错误的 GL 科目。

Fields used:

ITMRVA.Item class

Assumed standard list for MVP:

["FG", "RM", "PKG", "WIP", "EXP"]
# FG = Finished Goods
# RM = Raw Material
# PKG = Packaging
# WIP = Work in Process
# EXP = Expensed / Non-inventory


Trigger:

If Item class is null/blank
OR Item class not in the standard list above

→ Raise an issue.

Severity: medium

Example message:

Item class is 'MISC', which is not in the standard list [FG, RM, PKG, WIP, EXP]. Misclassification may cause costs to roll up to the wrong GL accounts.

5.5 Rule: ORPHAN_ITEM_SITE

Business name: Site-level records without a global Item Master entry

Business rationale:
如果某个 item 在 site 成本表 / 属性表里存在，但在 ITMENT 中不存在，全链路追踪会断裂，影响从交易到 GL 的对齐。

Fields used:

ITMRVA.Site identifier, ITMRVA.Item number

ITMRVB.Site identifier, ITMRVB.Item number

ITMENT.Item number

Trigger:

If (Site identifier, Item number) exists in ITMRVA or ITMRVB
BUT Item number does not exist in ITMENT

→ Raise an issue.

Severity: high

Example message:

Item N10006 exists at site MHP (attributes / cost) but is missing from ITMENT. This breaks traceability from transactions to the global item master.

6. ValidationResult Data Model（验证结果数据结构）

Agent 后端返回给前端的 JSON 建议使用如下结构（TypeScript 表示）：

type RuleId =
  | "INV_COST_MISSING"
  | "EXP_ITEM_WITH_INVENTORY_COST"
  | "UOM_MISMATCH"
  | "ITEM_CLASS_INVALID"
  | "ORPHAN_ITEM_SITE";

type IssueSeverity = "low" | "medium" | "high";

export interface ValidationIssue {
  site?: string;              // Site identifier, e.g., "MHP"
  item_number: string;        // Item number, e.g., "N10003"
  item_description?: string;  // From ITMENT
  rule_id: RuleId;
  severity: IssueSeverity;
  message: string;            // Human-readable issue description
  suggested_fix?: string;     // Optional recommended action
}

export interface ValidationStats {
  total_items: number;        // Distinct item numbers in ITMENT
  total_item_sites: number;   // Distinct (site, item) pairs seen
  total_sites: number;
  total_issues: number;
  issues_by_rule: Record<RuleId, number>;
  issues_by_severity: {
    low: number;
    medium: number;
    high: number;
  };
}

export interface ValidationResult {
  summary: string;            // Short text summary (can be simple, LLM will refine later)
  stats: ValidationStats;
  issues: ValidationIssue[];
}


这个结构将会被：

前端 UI 用来展示统计卡片和明细表；

LLM 模块（D）用来生成 executive summary 和 Q&A。

8. Agent Architecture for Vibe Coding（给 Cursor 拆分模块）

注意：下面只是“职责划分”，真正的 prompt 我们后面单独写。

A. Validation Engine Module

文件建议： src/lib/itemMasterValidation.ts

职责：

使用 xlsx / exceljs 读取上传的 workbook。

按 4.5 的逻辑构建 ItemSite 视图。

按第 5 章规则，生成 ValidationIssue[] 和 ValidationStats。

导出一个函数，例如：

export async function validateItemMaster(
  workbookBuffer: ArrayBuffer | Buffer
): Promise<ValidationResult> {
  // ...
}

B. API Route Module

文件建议：

App Router: app/api/validate/route.ts
或

Pages Router: pages/api/validate.ts

职责：

接收 multipart form 上传的 Excel 文件。

调用 validateItemMaster。

返回 ValidationResult JSON。

C. Frontend UI Module

文件建议：

App Router: app/page.tsx
或

Pages Router: pages/index.tsx + components

职责：

实现上传表单 → 调用 /api/validate。

展示 summary cards + issues table。

把 ValidationResult 传给 LLM 模块（D）或直接在前端调用 LLM API。

D. LLM Summary & Q&A Module

文件建议： src/lib/summaryAgent.ts

职责：

定义一个函数，例如：

export async function generateValidationSummary(
  result: ValidationResult
): Promise<string> {
  // call OpenAI/DeepSeek, return executive summary text
}


（可选）定义一个 Q&A 函数：

export async function answerUserQuestion(
  result: ValidationResult,
  question: string
): Promise<string> {
  // include result in the prompt, answer question
}


前端可以：

在验证完成后自动调用 generateValidationSummary 并展示在右侧面板；

在用户输入问题后调用 answerUserQuestion 实现“数据质检顾问”的对话体验。
